# 프로젝트 검토 및 VR 개발 가이드

> 3D VR 경쟁 폭탄해체 게임 — 초기 검토 문서 (2026-10-06)

---

## 0. 게임 개요

- 두 플레이어가 어두운 밀실의 테이블에 마주 앉는다. 천장 중앙에는 작은 조명 하나가 있다.
- 각 플레이어는 위협적인 외형의 **폭탄 조끼**를 착용하고, **상대 조끼의 기폭장치**를 들고 있다.
- 기폭장치에는 전선 m개가 있고, 그중 n개만 조끼와 연결되어 있다.
- 매 턴 중앙 우측 모니터에 문제가 나오고, **먼저 정답을 입력한 플레이어가 전선을 자를 기회**를 얻는다.
- 올바른 전선을 자르면 상대 목숨이 1 줄고, 줄어든 목숨은 계기판으로 확인한다. 올바른 전선을 모두 자르면 상대가 패배하고 상대의 조끼가 폭발한다.
- 일부 문제는 더 어려운 대신 **특수 능력**(절단 횟수 증가, 정답 전선 힌트 등)을 준다.
- 기폭 트리거가 될 전선은 **각 플레이어가 직접 선택**한다.

## 2. 기획 검토

### 🔴 핵심: 구조 설계가 바뀌는 결정

#### ① 멀티플레이 방식

- **온라인 1:1**이라면 "누가 먼저 맞혔나"를 **서버가 판정**해야 한다.
  - 핑 차이가 곧바로 불공정으로 이어진다. 호스트를 맡은 쪽이 유리하므로 서버 수신 시각 기준 판정이나 지연 보정이 필요하다.
- **숨겨진 정보**(어느 전선이 진짜인지)는 상대 클라이언트로 보내지 않는다.
  - 절단 결과만 서버가 알려주는 구조여야 치팅이 막힌다.
- 후보
  - Netcode for GameObjects + Relay/Lobby
  - Photon Fusion: Quest 크로스 매칭까지 생각하면 운영이 편한 편

#### ② VR 정답 입력 방식 (가장 큰 UX 리스크)

- VR에서 키보드 타이핑은 느리고, 느린 입력은 "빨리 입력하는 사람이 이긴다"는 경쟁 구도를 망가뜨린다.
- 권장 방식
  - **객관식 3~4지선다 + 테이블 위 물리 버튼**
  - **숫자 키패드** (산수, 코드 문제에 적합)
- 문제 유형은 입력 수단에 맞춰 설계한다. 주관식 텍스트 입력은 빼는 것을 권장한다.

#### ③ 규칙의 빈 곳

- [ ] **틀린 전선을 자르면?** 아무 일도 없는지, 자기 목숨이 줄어드는지, 다음 턴 입력이 막히는지 정해야 한다.
  - 페널티가 없으면 결국 전선 소거 게임이 되고, m-n개를 다 자르면 무조건 이긴다.
- [ ] **오답을 입력하면?** 제재가 없으면 버튼 연타가 최적 전략이 된다. 오답 시 해당 턴 입력 잠금 같은 제재를 권장한다.
- [ ] **둘 다 못 맞히면?** 타임아웃과 무승부 처리가 필요하다.
- [ ] **전선 비율 밸런스**: 전선 총수 m과 진짜 전선 수 n의 비율이 게임 길이를 결정한다. 예를 들어 m=8, n=3이면 평균 몇 턴이 걸리는지 미리 시뮬레이션한다.

#### ④ 기폭 전선 선택 단계: 심리전의 핵심

- 흐름: **설정 단계**(각자 자기 기폭장치에서 n개 선택) → **기폭장치 교환** → 본 게임
- 전선에 **색, 라벨, 위치 같은 구분 요소**가 있어야 "상대는 빨간색을 좋아할 것 같다" 같은 추측과 블러핑이 성립한다. 전선이 모두 같게 생기면 선택이 무의미해진다.
- 힌트 능력(예: "이 3개 중 1개는 진짜")도 이 구분 요소가 있어야 설계할 수 있다.

### 🟡 VR 구현 리스크

- **타깃 플랫폼** (Quest 단독 실행 가정)
  - "어두운 방 + 천장 조명 하나"는 **실시간 그림자 1개**로 비용을 제한하고 나머지는 베이크한다.
  - Quest 디스플레이는 어두운 장면에서 밴딩과 블랙 크러시가 심하다. 모니터, 계기판, 전선 색은 **자체 발광(Emissive)**으로 가독성을 확보한다.
  - 전선을 물리 로프로 만들면 비싸다. 스플라인이나 LineRenderer로 그리고 절단 시에만 연출하는 방식을 권장한다.
- **자기 조끼 보기**: 앉은 자세로 고개를 숙여 자기 조끼를 보게 되므로 **상체 IK 아바타**가 필요하다. 상대 조끼가 잘 보이도록 테이블 높이와 거리도 조정한다.
- **전선 절단 인터랙션**: 니퍼를 잡고(XRI Grab) 전선 콜라이더에 닿은 상태에서 트리거를 당기면 자르는 방식을 권장한다. 오조작 방지를 위해 절단 기회가 있을 때만 니퍼를 활성화한다.
- **멀미**: 앉아서 이동 없이 진행하므로 거의 문제없다. 폭발 연출 때 카메라를 흔들지 말고 화면 페이드나 비네트로 처리한다.

### 🟢 콘텐츠

- 문제 은행은 **데이터로 관리**(ScriptableObject 또는 JSON)하고 난이도, 유형, 보상 능력 필드를 둔다. 문제를 추가할 때 코드를 고칠 필요가 없어진다.
- 한글을 표시하려면 TextMeshPro용 한글 폰트 에셋이 필요하다.
- 특수 능력은 초기에는 2~3개만 둔다(절단 +1회, 힌트, 상대 입력 지연 등). 밸런스를 잡기 쉽다.

## 3. 권장 구조 (초안)

```
GameStateMachine: Lobby → WireSetup → [Question → Cut → Resolve]* → GameOver
├─ QuizService        문제 출제/정답 판정 (서버 권한)
├─ Detonator          전선 m개, 진짜 n개 (서버만 정답 보유)
├─ Wire               절단 가능 오브젝트, 결과 연출
├─ BombVest / Gauge   목숨 표시, 폭발 연출
├─ AbilitySystem      특수 능력 효과
└─ Net layer          턴/판정 동기화
```

### 입력과 로직의 분리

HMD 없이 개발하고, 봇 대전, 자동 테스트, 네트워크 테스트를 같은 경로로 돌리려면 게임 로직이 입력 방식을 몰라야 한다.

```
[VR 입력 (XRI)]  ─┐
[데스크톱 입력]  ─┼→  ICutCommand / IAnswerCommand  →  게임 로직 (입력 방식 모름)
[봇 AI]          ─┘
```

## 4. HMD 없이 개발하기

이 게임은 앉아서 하고 이동이 없어서 VR 게임 중에서도 HMD 의존도가 낮다. **개발의 70~80%는 HMD 없이 진행할 수 있다.**

### 4.1 도구

| 도구 | 용도 |
|---|---|
| **XR Device Simulator** (XRI 샘플) | 키보드와 마우스로 머리와 양손 컨트롤러를 조작한다. 잡기, 트리거, 버튼, UI 레이를 에디터 Play 모드에서 테스트한다. **기본 도구** |
| **Meta XR Simulator** | Quest 런타임을 흉내 낸다. 핸드 트래킹이나 Meta 전용 기능을 쓸 때 유용하다 (Quest 타깃일 때) |
| **데스크톱 테스트 모드** (직접 구현) | 마우스로 보고 클릭으로 전선을 자르고 숫자키로 정답을 입력한다. 규칙, 턴 진행, **멀티플레이 테스트**에 가장 빠르다. **강력 추천** |

> 멀티플레이 테스트는 에디터 한 개와 빌드 한 개, 또는 Multiplayer Play Mode로 두 플레이어를 띄워야 한다. HMD 두 대 없이 할 수 있는 현실적인 방법은 데스크톱 모드뿐이다.

### 4.2 HMD가 반드시 필요한 항목

| 항목 | 이유 |
|---|---|
| **스케일감** | 테이블 높이, 상대와의 거리, 전선 굵기. 모니터 화면으로는 거의 가늠이 안 된다 |
| **텍스트 가독성** | 모니터 문제 글자 크기, 계기판. VR 해상도에서 생각보다 훨씬 크게 만들어야 한다 |
| **어두운 조명** | 이 게임의 핵심 분위기. HMD 디스플레이에서는 모니터와 다르게 보인다 (블랙 크러시, 밴딩) |
| **손맛** | 니퍼로 전선을 자를 때의 판정 범위, 진동(Haptics), 사운드 타이밍 |
| **성능** | Quest 단독 실행이라면 72/90fps 유지 여부는 실기기로만 확인할 수 있다 |
| **멀미/피로** | 폭발 연출, 화면 효과 |

## 5. 개발 단계

| 단계 | 내용 | HMD |
|---|---|---|
| **1. 세팅** | XR 패키지(XRI, OpenXR), XR Origin, Device Simulator 세팅. 빈 씬을 HMD에서 한 번 띄워 **빌드 파이프라인이 동작하는지** 확인한다 | 1회 필요 |
| **2. 그레이박스** | 큐브로 방, 테이블, 의자, 모니터를 배치한다. HMD로 **스케일과 배치를 확정**한다 | 1회 필요 |
| **3. 핵심 규칙 프로토타입** | 상태 머신, 문제 출제, 전선 선택과 절단, 목숨 판정. 데스크톱 모드와 봇 상대로 **"재미있는가"를 검증**한다 | 불필요 |
| **4. 네트워크** | 에디터와 빌드 두 개로 1:1 동기화. 데스크톱 모드로 테스트한다 | 불필요 |
| **5. VR 인터랙션 다듬기** | 니퍼 잡기, 절단, 버튼 입력, 진동. 시뮬레이터로 만들고 실기기에서 몰아서 확인한다 | 주 1~2회 |
| **6. 아트, 조명, 연출** | 조명, 폭발 연출, 텍스트 가독성. HMD 의존도가 가장 높다 | 자주 |
| **7. 최적화와 실사용 테스트** | 프로파일링, 2인 실제 대전 플레이 테스트 | 필수 |

### 운영 팁

- 초반(규칙, 네트워크)은 HMD가 거의 필요 없고, 후반(연출, 최적화)으로 갈수록 필요하다.
- HMD를 쓸 수 있는 날에는 **점검할 항목을 미리 목록으로 만들어 두고** 몰아서 확인한다.
- 1단계 빌드 검증을 미루면 나중에 빌드 문제가 한꺼번에 터진다.
- 규칙은 네트워크 없이 먼저 검증하는 것이 가장 비용이 적게 든다.

## 6. 결정이 필요한 사항

- [ ] 멀티플레이 방식: **온라인 1:1**인가, **같은 공간 로컬**인가? 봇 대전도 포함하는가?
- [ ] 타깃 기기: **Quest 단독 실행**인가, **PCVR**인가? (설치할 OpenXR 기능 그룹, Android 빌드 설정이 달라짐)
- [ ] **틀린 전선 절단, 오답 입력 시 페널티**
- [ ] 정답 입력 방식: **객관식 버튼 방식** 채택 여부
- [ ] 전선 구분 요소(색, 라벨, 위치)와 m/n 수치
- [ ] 초기 특수 능력 목록
